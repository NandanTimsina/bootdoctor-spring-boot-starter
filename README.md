# BootDoctor

[![CI](https://github.com/NandanTimsina/bootdoctor-spring-boot-starter/actions/workflows/ci.yml/badge.svg)](https://github.com/NandanTimsina/bootdoctor-spring-boot-starter/actions/workflows/ci.yml)

**When your Spring Boot app fails to start, get a short plain-English diagnosis instead of a 100-line stack trace.**

BootDoctor is a Spring Boot starter. Add one dependency, and if your app crashes on startup it prints the likely cause, a suggested fix, how confident it is, and the exact lines of the error it based that on. Secrets are masked before anything leaves your machine, and if anything goes wrong inside BootDoctor, your app's own error is still printed as usual.

## Why I built it

Every Spring Boot beginner (including me) has stared at a wall of stack trace where the one useful line is buried near the bottom, under `Caused by:` three levels deep. Spring has built-in explanations for some failures, but not all. A refused database connection or a missing `${PLACEHOLDER}` still gives you the raw trace. BootDoctor fills that gap.

## What it looks like

My app was missing an environment variable. Spring printed a stack trace of 100+ lines. With BootDoctor added, this appears right before it:

```
BootDoctor: asking openai/gpt-oss-20b to explain this failure (waiting up to 8.0 s)...

======================================================================
 BootDoctor diagnosis
======================================================================
Likely cause : Missing JWT_SECRET property causing bean creation
               failure
Suggested fix: Add JWT_SECRET to application.properties or set as
               environment variable, e.g., JWT_SECRET=yourSecretKey
Confidence   : high
Evidence:
  - org.springframework.util.PlaceholderResolutionException: Could not
    resolve placeholder 'JWT_SECRET'
  - org.springframework.beans.factory.UnsatisfiedDependencyException:
    Error creating bean with name 'authTokenFilter': Unsatisfied
    dependency expressed through field 'jwtService'

AI-generated by openai/gpt-oss-20b in 2.2 s. It can be wrong, check before acting.
======================================================================
```

Same idea for a stopped database: it reports that the app cannot reach PostgreSQL at `localhost:5432` and that the database must be running, quoting the real error lines as evidence.

## Quick start

BootDoctor is not on Maven Central yet, so you install it from source (Java 17+, Maven):

```
git clone https://github.com/NandanTimsina/bootdoctor-spring-boot-starter.git
cd bootdoctor-spring-boot-starter
mvn install
```

Then add it to your Spring Boot app's `pom.xml`:

```xml
<dependency>
    <groupId>com.nandantimsina</groupId>
    <artifactId>bootdoctor-spring-boot-starter</artifactId>
    <version>0.1.0-SNAPSHOT</version>
</dependency>
```

BootDoctor needs an API key to ask the model. It uses [Groq](https://console.groq.com) (create a key there) and reads it from an environment variable, so the key never lives in your code or repo:

```
setx GROQ_API_KEY "your-key-here"      (Windows, then restart your IDE)
export GROQ_API_KEY="your-key-here"    (macOS / Linux)
```

Tested with Spring Boot 4.0.5 and 4.1.1. Older Spring Boot versions are untested.

## Settings

All optional. Put them in `application.properties` or pass them as environment variables.

| Property | Default | What it does |
|----------|---------|--------------|
| `bootdoctor.enabled` | `true` | Set to `false` to turn BootDoctor off completely |
| `bootdoctor.api-key` | `GROQ_API_KEY` env var | API key, if you don't want to use the env var |
| `bootdoctor.model` | `openai/gpt-oss-20b` | Which model to ask |
| `bootdoctor.base-url` | `https://api.groq.com/openai/v1` | Any OpenAI-compatible API |
| `bootdoctor.timeout-ms` | `8000` | How long to wait for the model |
| `bootdoctor.dry-run` | `false` | Print exactly what would be sent, and send nothing |

## What leaves your machine

Only a short, masked failure report:

- the Java and Spring Boot versions
- the exception chain (class names and messages, shortened)
- the top 8 stack frames of the root cause

Before anything is sent, a masking step hides passwords, tokens, API keys, credentials inside URLs and anything that looks like a secret. It deliberately over-masks. **Your configuration values and your files are never read or sent.** Want proof? Set `bootdoctor.dry-run=true` and BootDoctor prints the exact text it would have sent, then sends nothing.

## If something goes wrong

BootDoctor must never make a failing app fail worse:

- **No API key:** prints a one-line hint and the root cause.
- **Timeout, rate limit or network error:** prints one clear line and the root cause.
- **The model answers in a messy format:** prints the model's reply exactly as returned.
- **A bug inside BootDoctor itself:** swallowed. Spring's normal error output still appears.

These paths are covered by automated tests, and the full suite runs on every push.

## Results so far

I tried it on two of my own Spring Boot projects with real crashes:

| Failure | What was really wrong | BootDoctor's diagnosis | Result | Time |
|---------|----------------------|------------------------|--------|------|
| Missing environment variable | `JWT_SECRET` not set | Missing `JWT_SECRET` property | Correct | 2.2 s |
| Database not running | PostgreSQL container not started | Cannot connect to PostgreSQL at `localhost:5432`, make sure it is running | Correct | 1.7 s |
| Wrong database name | Database `trustengin` does not exist | Database does not exist, create it or fix the URL | Correct | 1.8 s |

That is **3 correct out of 3**, but it is a small sample from my own projects, not a benchmark. I have not yet tested port conflicts, circular dependencies, duplicate beans or other failure types.

## Limitations

- **It only covers startup failures.** Errors that happen while the app is running are not handled.
- **The answer is a model's opinion.** It can be wrong or vague, especially on unusual errors. The "confidence" value is what the model claims, not a measured accuracy. The evidence lines are there so you can check its reasoning.
- **It needs internet and an API key.** Without them you get a short hint instead of a diagnosis.
- **It adds a delay.** The model usually answers in about 2 seconds, and in the worst case BootDoctor waits up to the timeout (8 s by default) before Spring prints its own error.
- **The free API tier has rate limits.** If you hit them, BootDoctor shows a one-line message and your app is unaffected.
- **Masking is pattern-based.** It catches common secret formats and over-masks on purpose, but no pattern list is perfect. Use `bootdoctor.dry-run=true` to check what would be sent.
- **Prompt injection is reduced, not eliminated.** The error text is wrapped in tags and the model is told to treat it as data, but a model can still be misled by hostile text.
- **It does not replace Spring's own messages.** BootDoctor prints its box, and Spring's normal error output still follows.

## How it works

BootDoctor registers a Spring Boot `FailureAnalyzer`. Spring calls those when startup fails. This one never claims the failure. It prints its box and then lets Spring carry on as normal.

```
startup fails
   -> ContextCollector   builds a short report: versions, exception chain, top frames
   -> SecretMasker       hides passwords, tokens, keys and credentials in URLs
   -> PromptBuilder      wraps the report in a fixed instruction for the model
   -> GroqClient         sends it over HTTPS with timeouts
   -> ResponseParser     reads cause / fix / confidence / evidence, or keeps the raw reply
   -> ConsolePrinter     prints the box
```

`Diagnoser` runs this flow and handles the "no key", "dry-run" and "call failed" cases. `BootDoctorSettings` reads the `bootdoctor.*` settings.

## Design decisions

- **A `FailureAnalyzer`, not a log listener.** It is Spring's official hook for startup failures, and it runs before Spring prints the stack trace.
- **It always returns `null`.** If it returned a result, Spring would print only that and drop the stack trace. Returning `null` means BootDoctor can only add information, never remove it.
- **Mask first, then build the prompt.** Nothing unmasked is ever passed to the part that talks to the network.
- **No configuration values are sent.** The report is built from the exception only. Config often holds passwords, and the error message is almost always enough.
- **Dry-run exists to make the privacy claim checkable.** You can see exactly what would leave your machine.
- **The API key comes from an environment variable.** A key inside a published library would be shared by every user and could be extracted from the jar.
- **Groq with `gpt-oss-20b`.** An open-weight model behind an OpenAI-compatible API, so the base URL and model are settings you can change.
- **Spring Boot's own JSON parser.** Spring Boot 4 uses Jackson 3, while many dependencies still use Jackson 2. Using Boot's `JsonParserFactory` avoids a version clash in the host app.
- **Settings arrive through the constructor.** In Spring Boot 4, analyzers receive the `Environment` as a constructor argument. The older setter-based approach is not called.
- **The whole thing is wrapped in a catch-all.** A diagnosis tool must never be the reason an app fails.

## Tests

43 unit tests cover the masking rules, prompt building, the HTTP client (against a local fake server), response parsing, error handling and the report builder. No test needs a real API key or internet. GitHub Actions runs them on every push, on Linux with Java 17.

## Roadmap

Ideas for a next version, not promises: diagnose errors that happen while the app is running, group repeated errors so they are only explained once, support a local model through Ollama so nothing leaves the machine, and let users choose what is allowed to be sent.
